# Управление картографическими слоями

Тестовое задание: интерфейс управления слоями карты (температура, ветер, инсоляция) на React + TypeScript со state management на **vedro**.

## Запуск

```bash
npm install
npm run dev
```

## Архитектура

### Состояние

Стор описан одним объектом:

```ts
interface LayersState {
  layerIds: LayerId[];
  layers: Record<LayerId, LayerState>;
}
```

`layerIds` — стабильный список идентификаторов, `layers` — данные по каждому слою (`enabled`, `opacity`, `status`, `error`, `requestId`).

Такое разделение — ключевое решение для масштабируемости и производительности:

- `LayerList` подписан только на `layerIds` через `useLayersSelector`. Этот массив меняется только при добавлении/удалении слоя, поэтому список не перерисовывается при переключении/изменении прозрачности отдельных слоёв.
- Каждый `LayerItem` подписан только на свой `state.layers[id]`. При иммутабельном обновлении стора объекты остальных слоёв сохраняют ту же ссылку (`{ ...state.layers, [id]: ... }`), поэтому vedro не триггерит ререндер компонентов, чьи данные не изменились.
- `LayerItem` дополнительно обёрнут в `React.memo`.

В результате при переключении/изменении одного слоя перерисовывается ровно один компонент — независимо от того, 5 слоёв в списке или 100+. Проверялось логически через ссылочное сравнение объектов слоя, которое использует `useSelector` из vedro.

### Асинхронность и race condition

Каждый слой хранит счётчик `requestId`. При включении слоя или повторной попытке счётчик инкрементируется, и именно это значение "приклеивается" к конкретному mock-запросу (`runLayerRequest(dispatch, id, requestId)`).

Когда промис резолвится или падает, перед применением результата к стору проверяется:

```ts
if (layer.requestId !== requestId) {
  return {};
}
```

Если пользователь успел быстро выключить/включить слой (или нажать "повторить") ещё раз, `requestId` в сторе уже другой — устаревший ответ просто отбрасывается и не может перезаписать актуальное состояние. Это стандартный паттерн отмены "по номеру поколения" (аналог AbortController/epoch counter), без реальной отмены fetch, но с тем же эффектом консистентности.

### Слой действий

`store/layerActions.ts` отделяет бизнес-логику (переключение, повтор, изменение прозрачности) от компонентов. Компоненты только вызывают `toggleLayer`, `retryLayer`, `setLayerOpacity` и рендерят состояние — без побочных эффектов внутри JSX.

### Типизация

`any` не используется. Ошибка из mock API типизирована как `unknown` и сужается через `error instanceof Error`. Статусы — строгий union `'idle' | 'loading' | 'success' | 'error'`.

### Масштабируемость с 5 до 100+ слоёв

Список слоёв задаётся конфигом `LAYER_CONFIGS: LayerConfig[]` и строится в `buildInitialLayersState`. Чтобы получить 100+ слоёв, достаточно расширить этот массив конфигураций — остальная архитектура (стор, селекторы, компоненты) не завязана на конкретное количество и не потребует изменений. Рендер списка — `O(n)` по DOM, но обновление состояния одного слоя остаётся `O(1)` по перерисовкам благодаря точечным селекторам.

## Использование AI-инструментов

Решение подготовлено с использованием Claude (Anthropic) как AI-ассистента на всех этапах:

- **Исследование библиотеки.** У `vedro` (npm) минимальная документация без готовых практик для гонок состояний — Claude помог быстро разобрать API (`createVedro`, `useSelector`, `useDispatch`) и спроектировать поверх него архитектуру с точечными подписками.
- **Проектирование архитектуры.** Решение разделить состояние на `layerIds` и `layers` для минимизации перерисовок, а также паттерн `requestId` для гонок состояний — предложено и проверено логически вместе с Claude, включая разбор альтернатив (например, `AbortController`, который для mock-запроса избыточен).
- **Генерация кода.** Основной код компонентов, стора и mock API написан Claude по согласованной архитектуре, затем проверен вручную на соответствие условиям задания (типизация без `any`, обработка статусов, retry).
- **Ревью и документация.** Claude использовался для составления этого README и проверки, что архитектурные решения отвечают именно тем критериям, которые перечислены в задании (лишние render, гонки состояний, масштабируемость).

Ответственность за итоговый код и его корректность — на мне: код прочитан, логика гонок состояний и подписок проверена вручную перед отправкой.
